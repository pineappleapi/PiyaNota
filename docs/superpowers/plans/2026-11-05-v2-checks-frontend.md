### F2. Login wait after the 5th wrong password (J2). Sonnet. The server owns the ladder (contract J2: wrongs 1 to 4 free; 5 to 9 wait 30, 60, 90, 120, 150 s; the 10th starts a 1 hour lock, after which the server count steps back to 4 so the next wrong is wrong 5 and the ladder repeats). Delete the local failure count and its 24 h stale clock from `LoginThrottle` (keys `login_throttle.failures.*` and `.last.*`) and remove `recordFailure`: the app persists only the wait deadline derived from the server `retryAfterSeconds` and never infers a count; the 401 path records a wait only when `retryAfterSeconds` is present. No "1 try left" hint appears after a step-down; do not invent one locally. Clear any shown error or hint when a wait starts. Show 3600 s as 1:00:00 and do not wrap while counting down. Added acceptance: after the 10th wrong (shown 1:00:00) and the deadline passing, the next wrong shows a 0:30 wait; a correct password after the lock logs in; a correct password during the lock gets 429.. The app shows the live countdown from the `retryAfterSeconds` of the 401 and the `Retry-After` of a 429, and does not compute its own ladder for the real backend. During a wait or lock Log In is disabled and a "Forgot password" link stays active (a password reset clears the lock). The persisted wait is derived from the server value (the throttle lives in SharedPreferences with a wall-clock `until`, so clearing app data or changing the clock must not be the only guard). The fake backend implements the same J2 rule (stages as above). The app shows "N tries left" from `attemptsRemaining` only when it is 1. Network failures never count. A wrong password during the delete-account dialog does not count here.
Acceptance: four failures show "Incorrect email or password" with Log In enabled; the fifth disables Log In with a live 0:30 countdown; the sixth wait is 1:00; a success resets; a different email is independent; overflow test at 320 dp and 2.0x text.
